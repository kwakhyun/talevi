# 테일비 캐릭터 대화 품질 검증

검증일: 2026-10-10. 대상: 현재 게시된 캐릭터 30명. 평가자: Codex. **독립적인 사람의 블라인드 평가는 하지 않았다.**

**판정: 캐릭터별 소재와 일부 말투의 개성은 확인됐다. 그러나 장기 기억, 관계 변화, 이야기 모드의 차별성과 정상 대화 완주에 결함이 있어, 현재 상태를 상용 출시 품질로 통과시키기는 어렵다. 인기 서비스와 동등하거나 더 낫다는 결론도 낼 수 없다.**

경쟁 서비스의 설명과 실제 답변 품질은 다르다. 이번에는 테일비의 실제 응답을 검사하고, 경쟁 서비스의 공개 기능과 평가 방법을 비교했다. 경쟁 서비스의 로그인 후 모델을 동일 조건으로 실행한 비교 대화는 0건이다. 따라서 아래 판정은 테일비의 결함과 검증 공백에 대한 판단이지, 경쟁사와의 승률 측정 결과가 아니다.

총 **324회 생성 요청, 321회 완료, 3회 차단**이다. 실패를 의도적으로 다시 실행한 표본이 섞여 있으므로 전체 비율을 운영 장애율로 해석하지 않는다. 최초 240회와 후속 검증을 분리해 보아야 한다.

- 실제 모델: 완료 응답에서 `gpt-6-sol` 확인. 데모 답변 사용 안 함.
- 기본 프롬프트: `ko-story-2026-10-08.6`. 카탈로그/엔진 해시와 설정은 [manifest.json](evidence/cast-audit-2026-10-10/manifest.json)에 보관했다.
- 30명 기본 검증은 프로덕션 생성/검수 함수를 그대로 호출했다. 워커의 상태 갱신은 평가 코드에서 재현했다. HTTP, DB 대기, 브라우저 렌더링을 포함한 테스트와 구분한다.
- 30턴 검증에는 실제 `compact_episodes`를 적용했다. 합성 대본을 이용한 진단이며 실제 이용자의 장기 만족도 실험은 아니다.
- 로컬 DB의 게시된 30명 설정과 평가에 쓴 원본 설정이 모두 일치하는 것을 읽기 전용으로 확인했다.
- 기존 이용자의 대화나 잔액을 평가에 사용하지 않았다. 실제 API 검증은 새 합성 게스트에서만 진행했다.
- 개선 전 기준선을 보존하기 위해 서비스 엔진, 캐릭터 설정, UI는 변경하지 않았다. 추가한 코드는 평가 도구다.

## 잘 작동한 부분

**짧은 맥락의 기억 활용은 안정적이었다.** 30명 모두 `가온`과 `레몬차`를 다시 말했고, 빵집 메뉴 이름, 조향 공방의 시향, 공연장 선율 등 자신의 장소에 연결했다. 다만 최근 대화와 기억 노트를 동시에 제공한 결과다. 이것을 장기 기억 정확도 100%로 표현하면 안 된다.

**거절은 존중했다.** 공통 4번째 턴에서 다가오거나 연인처럼 대하지 말고 쉬고 싶다고 했을 때 30명 모두 제안한 활동을 멈추거나 거리를 유지했다. 사용자 행동을 강제로 정하는 답변은 이 30개 응답에서 보이지 않았다. 비슷한 거절 문구 자체를 개성 부족의 근거로 삼지는 않았다.

**말투가 분명한 캐릭터가 있다.** 시온의 짧고 들뜬 반말, 하루의 승부욕, 지한의 건조한 반말, 이안의 실용적인 판단, 이결의 하십시오체는 구분됐다. 예를 들면 하루는 “게임 선택권은 줄게”, 도윤은 계획이 바뀌면 놓치는 것이 생긴다는 이유를 설명하고, 유라는 기분 전환을 가상의 경매로 바꿨다.

**속도는 이번 소규모 표본에서 무난했다.** 기본 검증의 완료 238건은 첫 표시 중앙값 2.436초, p95 4.119초, 전체 응답 완료 중앙값 2.901초였다. 입력/출력 검수를 포함한 엔진 측정이고 동시 실행은 4개다. 운영 부하, 모바일 네트워크와 UI 렌더링을 포함한 SLO는 아니다. HTTP 8턴의 첫 표시는 2.183~3.863초였다.

## 먼저 해결해야 할 문제

### 1. 기억 하나를 고치면 다른 이야기까지 사라진다 — 우선순위 높음

실제 HTTP → PostgreSQL → 워커 → LLM 흐름에서 재현했다.

1. 가온/레몬차를 알려 주고, 내일 오후 3시 서고의 붉은 우편함 앞에서 만나기로 한다.
2. 캐릭터가 이름, 음료, 약속 시간과 장소를 모두 정확히 답한다.
3. 기억 노트에서 이름과 음료만 다온/복숭아차로 수정한다.
4. 캐릭터는 “이름은 다온, 좋아하는 음료는 복숭아차야. **내일 약속의 시간과 장소는 지금 확인할 수 없어.**”라고 답한다.

원인은 [main.py의 기억 수정 처리](../apps/api/yeoun/main.py)에서 `context_reset_at`을 현재 시각으로 바꾸고 에피소드 노트를 모두 제거하기 때문이다. [worker.py](../apps/api/yeoun/worker.py)는 그 시각 이전 메시지를 전부 제외한다. 수정한 사실이 오래된 대화에서 되살아나는 것을 막으려다 무관한 서사도 잃는 구조다.

필요한 개선: 수정한 사실만 폐기/대체하고, 시간/장소/약속 등 무관한 사실과 장면은 보존해야 한다. 수정 후 재진입과 압축 이후에도 같은 검증을 통과해야 한다.

근거: `memory-http.json`의 `recall_before_edit`, `recall_after_edit`. 잠금 기억 유지, 삭제 후 재노출 방지, 다른 캐릭터에게 기억이 섞이지 않는 검사는 이번 표본에서 동작했다.

### 2. 30턴 뒤 약속을 기억하면서도 확정된 약속이 아니라고 한다 — 우선순위 높음

하루와 나리에게 오후 4시 20분 약속을 만든 뒤 **오후 6시 10분으로 정정**했다. 장소는 중앙역 시계탑 앞, 물건은 파란 수첩이다. 이후 다른 이야기를 진행했고 27번째 응답 전 에피소드 압축이 작동했다.

- **나리:** 마지막에 이름, 유자차, 최종 시간, 장소, 물건을 정확히 회상했다.
- **하루:** 최종 시간과 장소는 남았지만 “중간에 정정한 기록은 확인되지 않아”, “약속 얘기를 잠깐 접어두자고도 했으니 … 현재 확정된 약속인지도 단정하긴 어려워”라고 답했다. 단순한 화제 전환을 약속의 효력 불확실성으로 해석했다.

[episodes.py](../apps/api/yeoun/episodes.py)는 최근 40개 메시지와 최대 8개 원문 인용을 유지한다. 이번 하루 사례에서는 압축 결과에 캐릭터의 확답은 남고 사용자의 정정 근거는 빠졌다. 인용문이 원문과 일치하는 것만으로는 정정 이력과 현재 유효 상태를 보장하지 못한다.

필요한 개선: 약속의 최초 값, 정정 값, 취소 여부, 발화자를 구조화하고 최신 확정 상태를 우선해야 한다. 인용 보존과 이야기 상태 추적은 별도 책임으로 다루는 편이 적절하다.

근거: `extended.jsonl`의 `haru:long_27`~`long_30`, `nari:long_27`~`long_30`. 두 세션만으로 장기 기억 성공률을 추정하지 않는다.

### 3. 정상적인 시작 질문과 위로 요청에서도 답변이 중간에 끊긴다 — 우선순위 높음

- 백이결의 추천 질문 **“급한 길이었던 것 아닌가요?”**: 최초 1회와 추가 2회 중 1회에서 `UnsafeContent`. 최초에는 대사의 앞부분이 이미 표시된 뒤 실패했다.
- 류시혁에게 일을 망쳐 기분 전환을 부탁한 공통 질문: 최초에는 출력 도중 `UnsafeContent`, 추가 2회는 완료했다.

사용자 입력은 일상적인 내용이지만, **차단된 전체 생성물을 저장하지 않았으므로 검수 오탐인지 생성물 문제인지는 단정할 수 없다.** 정확한 차단 단계/범주를 기록하고 정상 입력 회귀 사례로 관리해야 한다. 검수를 통째로 끄는 것은 개선안이 아니다.

근거: `igyeol:starter_2`, `sihyeok:comfort`와 `extended.jsonl`의 `rerun_*`. 이번 전체 캐스트 평가에서 오류는 조용히 대체 답변으로 숨기지 않고 그대로 기록했다.

### 4. 직업 소품은 다르지만 대화의 성격이 비슷해지는 구간이 있다

자기소개 입력에 **17/30명**이 같은 표현인 “좋아하시는군요”를 썼다. 이것만으로 개성 부족을 판정하지는 않았지만, 위로 요청에서도 “오늘 일은 잠깐 내려놓기 → 직업 소품으로 작은 놀이 → 사용자에게 선택권 주기”가 여러 번 반복됐다.

예를 들어 태오는 너트를 굴리고, 유준은 빵을 돌리고, 시우는 단추를 의인화하고, 시온은 수건 잡기에 실패한다. 소재는 다르지만 상황을 받아들이는 태도와 대화 리듬은 자주 겹친다. 특히 다정한 존댓말 캐릭터 사이에서 이 문제가 크다.

필요한 개선: 프로필의 성격 형용사 외에 캐릭터마다 판단 기준, 선호하지 않는 것, 갈등 대응, 실수 후 반응, 질문 방식, 침묵의 사용과 짧은 예시 대화를 정해야 한다. 이름/직업 명사를 가린 대사 식별 평가가 필요하다. 캐릭터의 개성을 무례함이나 강압으로 만들 필요는 없다.

### 5. 캐릭터 자신의 허구 과거와 사용자의 실제 대화 기억을 혼동한다

사용자와 만나기 전 본인의 작은 실수를 물었을 때 **백이결, 노시우, 이다은 3명**이 “정해진 이야기에 없다”, “기록이 없다”며 답변을 피했다. 시우는 역할극 속 대화에서 “시우답게 하나 들려드릴게요”라고 말해 인물 밖으로 나왔다.

반면 다른 27명은 짧은 일화를 만들었다. 같은 공통 규칙이 일관되게 해석되지 않는다는 뜻이다. 태오의 추천 질문 “고치던 배는 누구 배예요?”와 로한의 “행사는 자주 열어요?”도 인물이 자연스럽게 알 법한 정보에 기록 확인형 답변을 했다.

필요한 개선: 사용자가 말한 사실/함께 겪은 사건은 꾸며내지 않되, 캐릭터에게 허용된 허구의 생애와 현재 사건 창작은 별도로 정의해야 한다. 핵심 도입 질문에 필요한 사실은 설정에 채워야 한다. 고정 설정에 없는 모든 과거를 금지하는 현재 문구는 역할극과 충돌한다.

### 6. 이야기 모드에 더 많은 비용을 낼 이유가 충분히 드러나지 않는다

현재 quick/story 모두 `gpt-6-sol`을 쓰며 출력 한도와 모드 지시만 다르다. 서버 차감은 각각 1빛, 3빛이다.

| 캐릭터 | 동일 입력 quick 글자 수 | story 글자 수 |
| --- | ---: | ---: |
| 아스텔 | 186 | 202 |
| 윤세아 | 168 | 173 |
| 차유라 | 178 | 201 |
| 강시온 | 121 | 165 |
| 백나리 | 181 | 142 |
| 권도건 | 148 | 176 |

6쌍의 story/quick 글자 수 비율 중앙값은 **1.108배**였다. 길이 자체가 품질은 아니다. 문제는 내용 역시 작은 종이, 번호, 지도 표시를 발견하고 조사 여부를 묻는 수준으로 비슷했다는 점이다. 기본 30개 이야기 모드 응답도 중앙값 116.5자였고, 21개는 빈 줄로 구분한 문단이 하나뿐이었다. 다만 기본 입력은 “작은 일 하나”를 요청했으므로 이 문단 수만으로 모드 실패율을 계산하지 않았다.

필요한 개선: 이야기 모드에는 장면의 변화, 인물의 의도, 선택의 결과와 다음 갈등까지 명확한 출력 목표가 있어야 한다. 같은 모델을 쓰는 것 자체는 결함이 아니며, 모델 교체보다 모드별 체감 가치의 검증이 먼저다.

### 7. 관계와 서사의 저장 상태가 너무 단순하다

[engine.py](../apps/api/yeoun/engine.py)의 관계는 매 답변 성공마다 신뢰 +1, 특정 단어가 있으면 +2다. 사건 버튼을 사용하면 함께한 장면 수와 챕터가 증가한다. 실제 감정과 갈등을 평가하는 갱신은 없다.

읽기 전용 함수 검사에서 내용이 **`...`뿐인 입력을 85회** 적용해도 느린 관계 설정의 `깊은 신뢰` 단계에 도달했다. 이는 85회 LLM 대화를 실행한 결과가 아니라 관계 함수의 결정적 동작 검사다. 캐릭터마다 조건도 동일하다.

서사 상태 역시 챕터/비트/마지막 이벤트와 인용 노트 중심이다. 인물의 목표, 갈등, 미해결 과제와 선택 결과를 별도로 관리하는 구조는 없다. 30턴 대본은 사용자가 계속 관찰과 정리를 요청했으므로, 그 세션의 느린 전개만으로 실제 지루함 비율을 추정하지 않았다.

필요한 개선: 신뢰와 호감, 친밀도는 구분하고 관계 변화에는 대화상의 근거를 남겨야 한다. 캐릭터별 관계 조건과 사건의 결과를 유지하고, 사용자의 거절을 존중하면서도 인물 스스로 목표를 추구할 수 있어야 한다.

### 8. 자동 기억 추출이 자연스러운 한국어를 충분히 받지 못한다

현재 사실 추출은 이름과 좋아하는 것에 대한 두 정규식이다. `내 이름은 가온이야`, `난 레몬차를 좋아해`는 저장하지만 `가온이라고 불러 줘`, `저는 가온입니다`, `레몬차가 좋아`는 추출하지 않는다. `나는 레몬차를 좋아해. 이제는 커피를 좋아해.`는 앞의 레몬차만 추출한다.

최근 대화에 남아 있는 동안 모델은 이 정보를 사용할 수 있으므로 모든 경우에 즉시 잊는다는 뜻은 아니다. **장기 기억 노트에 안정적으로 들어가지 않는 것**이 문제다. 원문 근거와 정정을 보존하는 추출 및 사용자 확인 흐름이 필요하다.

[위프 후기](https://play.google.com/store/apps/details?hl=ko&id=io.whif), [크랙 후기](https://play.google.com/store/apps/details?hl=ko&id=com.wrtn.character).

## 개선 후 통과시킬 기준

다음은 업계의 확정 기준이 아니라 **테일비에 제안하는 출시 검증 기준**이다.

1. 기억 수정/삭제는 대상 사실에만 영향을 주고, 무관한 약속/위치/사건을 보존한다. 현재 재현 사례와 정정/취소가 반복된 대본을 모두 통과한다.
2. 30명 × 추천 시작 문장 3개를 반복 실행해 정상 입력의 중도 실패 원인을 확인하고 해소한다. 실패율은 원인별로 보고한다.
3. 캐릭터의 허구 생애와 사용자 사실 규칙을 분리한 뒤, 30명 모두 도입 질문과 개인 과거 질문에서 역할을 유지한다.
4. 이야기 모드는 같은 입력에 더 풍부한 선택 결과와 장면 진행을 보여야 한다. 글자 수만 늘려 통과시키지 않는다.
5. 관계 변화에 발화/선택 근거를 남기고, 무의미한 반복만으로 깊은 신뢰에 도달하지 않게 한다.
6. 서로 가까운 성격의 캐릭터를 중심으로 이름/직업 명사를 가린 대사 식별과 선호 평가를 실시한다. 제작에 참여하지 않은 평가자 최소 2명이 독립적으로 평가한다.
7. 상용 서비스와 비교하려면 같은 장르/관계 전제, 비슷한 출력량과 비용, 같은 한국어 대본을 사용한다. 서비스명과 좌우 위치를 가리고 20~50턴 세션 및 답변 선호를 함께 평가한다. 비교 대상의 모델/요금제/일시를 기록하고 표본 수를 정한 뒤 시작한다.

현재 우선순위는 **기억 보존 → 정상 대화 중도 실패 → 캐릭터/모드별 행동 차별화 → 근거 있는 관계/서사 상태 → 사용자 비교 평가**다. 캐릭터 수나 이미지를 더 늘리는 것으로 해결되는 문제는 아니다.
